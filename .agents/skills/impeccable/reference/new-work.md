# New visual work

Use for a genuinely new surface or a requested replacement identity, not a local
component addition. The owning web instructions establish visual authority:
live Paper is authoritative; PRODUCT.md/DESIGN.md and snapshots preserve context.

## Establish the design problem

Inspect the relevant live screens, states, tokens, code and supplied content.
Preserve an established world when extending it. A missing Markdown file is not
proof of a greenfield design. Distinguish a local extension, brand expansion and
an explicitly requested replacement. Resolve purpose, audience, primary action,
content ranges, states and meaningful exclusions from available evidence; ask only
about a material unresolved design choice, not settled facts or routine CSS values.

## Develop the composition

For new surfaces/substantial redesign, explore the composition in Paper and agree
it with the user before application UI coding. Reuse prior agreement; there is no
second compulsory comp tournament or confirmation. Develop alternatives only
when they clarify a genuinely open choice, not to satisfy a fixed count or dice
roll. Preserve factual copy, behavior, privacy, error states and accessibility.

Choose hierarchy for the actual task: persuasion needs evidence and an action;
operational screens prioritize completion and scanability; reading needs structure
and navigation; experiential work may foreground interaction. The mode is a design
aid, not a new planning system. Existing surface briefs remain compatible tool
inputs; ongoing implementation and acceptance belong in the owning outcome plan.

## Implement and verify

Build the agreed composition with semantic components, real content and the
existing token system. A reference image guides visual fidelity; it is not a
reason to rasterize text or controls. Use [visualization](visualize.md) only when
it helps the actual task, and relevant typography/layout/interaction references
when needed. No automatic build-phase ledger or fixed reviewer team is required.

Inspect affected desktop/mobile states, keyboard/focus/error paths and applicable
reduced motion. Fix material in-scope failures and verify those fixes. Broaden
verification for new evidence gaps, not a fixed ritual. A first implementation is
not completion; neither an arbitrary pass ceiling nor a tool's score establishes
acceptance. Do not claim independent review or runtime evidence that did not occur.
