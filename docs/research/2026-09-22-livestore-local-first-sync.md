# LiveStore as a future local-first sync engine

Research date: 2026-09-22. This is an assessment, not a storage decision or an implementation plan. No LiveStore package or application path has been changed.

## Recommendation

Revisit LiveStore when a completed household flow needs broader offline editing or live collaboration. Do not adopt it to fix the current onboarding dialog behavior. Setup checkpoints are saved on user actions, and the dialog issue is an unnecessary wait for a checkpoint write and session refetch. A sync engine would add another data path without addressing that UI dependency.

LiveStore is a plausible match for a **new, self-contained local-first feature**: it provides local SQLite queries, an event log, React integration, and first-party Cloudflare sync over WebSocket, HTTP or Durable Object RPC. Its Cloudflare sync backend defaults to Durable Object SQLite and can use D1. It also has an Effect integration. Version 0.4.0 is a [published release](https://github.com/livestorejs/livestore/releases/tag/v0.4.0), not an unreleased documentation example. See the [Cloudflare provider](https://docs.livestore.dev/sync-providers/cloudflare/), [Cloudflare adapter](https://docs.livestore.dev/platform-adapters/cloudflare-durable-object-adapter/) and [release notes](https://docs.livestore.dev/changelog/).

The existing household domain is a harder fit. [Household authority](../explanation/household-authority.md) makes each household's SQLite-backed `HouseholdObject` the canonical product store. The [household boundary](../reference/household.md) checks Better Auth membership before routing, then uses server-owned identities, time, versions and retry receipts in local transactions. LiveStore instead treats its local event log as the source of truth and the backend as an event orderer and distributor. Its own [fit guide](https://docs.livestore.dev/overview/when-livestore/) flags an existing authoritative database or server-primary data flow as a poor fit. Syncing the same household facts in both systems would create competing authorities; making LiveStore a cache of `HouseholdObject` would leave much of its event model unused.

## Boundaries a future design must prove

- **Identity and isolation.** A `storeId` can scope one event log to one household, but the client supplies it in the sync request. The sync Worker must derive or verify the immutable organization and current Better Auth membership before any pull or push. LiveStore does not include authorization. Its [auth guidance](https://docs.livestore.dev/patterns/auth/) says connection validation runs once, while `onPush` and `onPull` must check the original client payload again; it also notes that HTTP does not currently forward that payload. The same guidance describes forwarded cookies for WebSocket callbacks. A pilot must prove role changes and member departure while a connection is open and when an offline device reconnects.
- **Commands and conflicts.** [ADR-0009](../decisions/adr-0009-synchronize-shopping-lists-through-idempotent-item-operations.md) allows only narrow offline shopping operations. They remain pending until the household authority accepts them; stale targets and structural changes need explicit conflict results. A future LiveStore design must show how it rejects a specific invalid event, reconciles the optimistic local view, preserves an operation ID and original request after an unknown outcome, and assigns authoritative time, order, versions and receipts. LiveStore's [event-rejection issue](https://github.com/livestorejs/livestore/issues/404) is open and describes a rejected event blocking later events in the chain. The documented `onPush` hook alone is not evidence that Meal Planner's command contract is covered.
- **Atomicity and side effects.** Imports, plan decisions and other commands can atomically save product state, retry receipts and outbox intent inside `HouseholdObject`; provider and Workflow calls happen after commit. A separate LiveStore sync Durable Object cannot share that transaction. Moving a feature would require redesigning its owning command path, not dual-writing events and household rows. See [household authority](../explanation/household-authority.md).
- **Privacy and revocation.** Shared household events must never contain participant-private transcripts, tentative interview cards, raw evidence, provider credentials or large R2 files. [Private discovery](../reference/private-discovery.md) checks access immediately before each private socket send and requires fresh review after a stale confirmation. A synced browser database persists data on devices; blocking future sync does not erase copies already held there. A future design needs explicit local-store deletion on logout and household switch, a purge or lockout when a revoked device reconnects, and a policy for data already viewed.
- **Evolution and operations.** LiveStore is [in beta](https://docs.livestore.dev/misc/state-of-the-project/) with no 1.0 date; minor releases can change client or sync-backend storage formats, and event-log compaction remains future work. [App evolution](https://docs.livestore.dev/patterns/app-evolution/) requires handling old clients that encounter new events. The [production checklist](https://docs.livestore.dev/building-with-livestore/production-checklist/) is currently incomplete. A production proposal needs restore, deletion, migration, rollout and old-client behavior proved against the exact chosen release.

## Small later experiment

Use an isolated two-browser prototype of shared shopping items: manually add an item and set its checked state to a desired value. Test concurrent edits, offline replay, stale item identity, a revoked member's reconnect, rejected operations, schema upgrades and local cache clearing. Keep this prototype outside the application and exclude plan-derived quantities, private data and provider work. Shopping is the clearest product case for offline collaboration, but [the shopping-list stage](../plans/shopping-list.md) is still proposed, and its accepted [operation contract](../decisions/adr-0009-synchronize-shopping-lists-through-idempotent-item-operations.md) remains the baseline.

If the experiment succeeds and its benefits justify the change, first choose one authoritative owner for that feature and revise the relevant decision record. Estimate the replacement of command and query paths, receipts and conflict UI, per-household data import, authentication hooks, Alchemy bindings, migration and recovery tooling. No such migration is authorized by this research note.
